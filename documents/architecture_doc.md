# Задания 7-10

## Задание 7. Проектирование схем коллекций для шардирования данных

### Введение

Дано:
БД MongoDB. 3 коллекции orders, products и carts с их описанием(опускаю для краткости).

Требуется:

* Спроектировать схемы коллекций products, orders и carts. Для этого проанализировать представленные атрибуты коллекций
  и выбрать потенциальных кандидатов для шард-ключей.
* Выберать стратегию шардирования для каждой коллекции, которая обеспечит эффективное распределение данных по шардам.
* Указать, почему выбранная стратегия и шард-ключ подходят под особенности коллекций и операций.

### Термины

Хэшированное шардирование (англ. key based sharding) — это разделение данных на шарды на основе хэш-функции от значения шард-ключа. Обеспечивает равномерное распределение даже для монотонно возрастающих ключей.

Диапазонное шардирование (англ. range based sharding) —  разделение данных на шарды на основе диапазонов значений шард-ключа (chunks). Эффективно для запросов, фильтрующих по диапазону или сортирующих по ключу.

Targeted-запрос – запрос, который содержит полный шард-ключ (или его префикс) и направляется только в те шарды, где
могут быть данные. Быстрый, минимальная нагрузка на кластер.

Broadcast-запрос – запрос, который не содержит шард-ключ (или содержит его не полностью) и поэтому отправляется во все
шарды. Каждый шард выполняет поиск самостоятельно, результаты объединяются. Медленнее, создаёт дополнительную нагрузку.

### Особенности алгоритмиов шардированию данных

#### Хэшированное шардирование
* Равномерное распределение данных (устраняет hotspot). 
* Затруднён поиск по диапазону (требует broadcast)..
  
Применение алгоритма оптимально для приложений, в которых крайне важно равномерно распределить данные. Например, при хранении пользовательских сессий в веб-приложениях или товаров в магазине.

#### Диапазонное шардирование
* Быстрый поиск по диапазону и сортировка (при использовании префикса ключа). 
* Риск дисбаланса (hotspot) при монотонном ключе..
  
Подходит для данных временных рядов или последовательных данных, таких как журналы, события с временными метками, цены на товары и т. д.

#### Общий принцип

Стремиться к тому, чтобы наиболее частые и критичные операции были targeted-запросами, избегая broadcast для тяжелых запросов. Также важно равномерно распределять данные и нагрузку по шардам, не допуская появления «горячих» шардов.

### Проект решения
### 1. Коллекция orders
#### 1.1. Схема документа в коллекции orders

```json
{
  "_id": "UUID",
  "customer_id": "UUID",
  "created_at": "Date",
  "items": [
    {
      "product_id": "UUID",
      "name": "string",
      "quantity": "int",
      "price": "Decimal128"
    }
  ],
  "status": "string (created|paid|shipped|delivered|cancelled)",
  "total": "Decimal128",
  "geo_zone": "string"
}
```
"_id" - id заказа

#### 1.2. Операции и их требования к шард-ключу

| Операция                                        | Какие поля фильтра                     | Желаемый тип запроса                | Почему                                                | Какие поля должны быть в шард-ключе    |
|-------------------------------------------------|----------------------------------------|-------------------------------------|-------------------------------------------------------|----------------------------------------|
| Создание заказа (вставка)                       | – (нет фильтра)                        | равномерное распределение по шардам | Избежать «горячей» точки (hotspot) при записи         | customer_id                            |
| Поиск истории заказов конкретного пользователя. | customer_id + сортировка по created_at | targeted                            | Частая операция, должна быть быстрой и масштабируемой | customer_id и created_at (как суффикс) |
| Отображение статуса заказа.                     | _id                                    | targeted (желательно)               | Обращение по уникальному идентификатору, тоже часто   | необязательно, допустим broadcast      |

#### 1.3. Анализ кандидатов в шард-ключ

| Кандидат                                 | Тип шардирования                   | Операции, которые станут targeted                                                   | Проблемы                                                                                          |
|------------------------------------------|------------------------------------|-------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------|
| { _id: "hashed" }                        | hashed                             | просмотр статуса                                                                    | История клиента – broadcast (и сортировка по дате неэффективна)                                   |
| { customer_id: 1, created_at: 1 }        | ranged (по клиенту, затем по дате) | история клиента (и сортировка по дате)                                              | Вставка: монотонность customer_id может дать 'горячий шард', если ID генерируются последовательно |
| { customer_id: "hashed", created_at: 1 } | hashed-префикс + диапазон          | история клиента (направляется в один шард по хэшу, внутри шарда сортировка по дате) | Просмотр статуса – broadcast                                                                      |

#### 1.4. Выбранное решение

Шардирование

```javascript
sh.shardCollection("market.orders", { customer_id: "hashed", created_at: 1 })
```

Почему именно этот составной ключ?

1. Хэширование customer_id
    * Равномерно распределяет заказы по шардам, полностью убирая hotspot (даже если ID клиента монотонны).
    * Любой запрос с фильтром по customer_id (даже без created_at) становится targeted, потому что хэш-префикс
      совпадает.

2. Диапазонная часть created_at
    * Позволяет внутри шарда эффективно выполнять сортировку по дате для истории заказов одного клиента.
    * Запрос { customer_id: X, created_at: { $gte: ... } } остаётся targeted.
3. Просмотр статуса по _id
    * Становится broadcast, но эта операция легковесна (один документ на шарде) и ускорена встроенным уникальным индексом.
    * Мы сознательно жертвуем этой операцией в пользу более частой истории заказов.

Варианты, которые оказались хуже:

* { _id: "hashed" } – история клиента стала бы broadcast, что неприемлемо для высоконагруженного сервиса.
* { customer_id: 1, created_at: 1 } (без хэша) – при монотонном customer_id новые заказы активных клиентов могли бы
  попадать в один шард (hotspot).

#### 1.5. Как выглядит выполнение запросов после шардирования

| Запрос                                                          | Тип                    | Объяснение                                                                                                                                |
|-----------------------------------------------------------------|------------------------|-------------------------------------------------------------------------------------------------------------------------------------------|
| db.orders.find({ customer_id: "123" }).sort({ created_at: -1 }) | targeted               | Хэш от customer_id направляет запрос в точный шард, внутри шарда используется индекс по created_at.                                       |
| db.orders.findOne({ _id: "abc" })                               | broadcast              | Запрос идёт во все шарды, но уникальный индекс на _id позволит быстро найти документ на каждом шарде (только один шард вернёт результат). | 
| db.orders.insert({ ... })                                       | распределённая вставка | Хэш от customer_id определяет шард, в который попадёт новый заказ (без «горячей» точки).                                                  |

#### 1.6. Дополнительные индексы для ускорения доступа
Исходя из указанных в задании типовых операций не требуются

### 2. Коллекция products
#### 2.1. Схема документа в коллекции products

```json
{
   "_id": "UUID",
   "name": "string",
   "category": "string",
   "price": "Decimal128",
   "stock": [
      { "geo_zone": "string", "quantity": "int" }
   ],
   "attributes": {
      "color": "string",
      "size": "string"
   },
   "created_at": "Date",
   "updated_at": "Date"
}
```
"_id" - уникальный идентификатор товара

#### 2.2. Операции и их требования к шард-ключу

| Операция                                   | Какие поля фильтра | Желаемый тип запроса | Почему                           | Какие поля должны быть в шард-ключе |
|--------------------------------------------|--------------------|----------------------|----------------------------------|-------------------------------------|
| Обновление остатка товара при покупке      | _id                | targeted             | очень часто, критично к задержке | _id                                 |
| Чтение карточки товара (страница продукта) | _id                | targeted             | часто, пользовательский опыт     | _id                                 |
| Поиск товаров по категории и диапазону цен | category, price    | broadcast (допустим) | менее частый, можно кешировать   | не требуется                        |

#### 2.3. Анализ кандидатов в шард-ключ

| Кандидат                | Тип шардирования | Операции, которые станут targeted   | Проблемы                                                                  |
|-------------------------|------------------|-------------------------------------|---------------------------------------------------------------------------|
| { _id: "hashed" }       | hashed           | обновление остатка, карточка товара | поиск по категории/цене – broadcast                                       |
| { category: "hashed" }  | hashed           | поиск по категории                  | обновление остатка и карточка – broadcast (плохо)                         |
| { category: 1, _id: 1 } | ranged           | поиск по категории (префикс)        | обновление остатка – broadcast, плюс jumbo-куски на популярных категориях |

#### 2.4. Выбранное решение

Шардирование

```javascript
sh.shardCollection("market.products", { _id: "hashed" })
```

Почему именно этот ключ?

1. Операции с _id – самые частые и критичные
    * Обновление остатков и чтение карточки товара выполняются постоянно. Хэшированный _id делает эти запросы targeted и идеально распределяет нагрузку по шардам (даже если _id генерируется монотонно, хэш устраняет hotspot).

2. Поиск по категории и цене – broadcast, но это компромисс
    * Такой поиск выполняется реже, его результаты можно кешировать. На каждом шарде он будет использовать вторичный индекс { category: 1, price: 1 }, что приемлемо.

Варианты, которые оказались хуже:

* { category: "hashed" } – превратила бы частые обновления остатков в broadcast, что неприемлемо.
* { category: 1, _id: 1 } (диапазонное) – привела бы к jumbo-кускам на больших категориях (например, «Электроника») и перекосу записи.

#### 2.5. Как выглядит выполнение запросов после шардирования

| Запрос                                                                        | Тип       | Объяснение                                                                            |
|-------------------------------------------------------------------------------|-----------|---------------------------------------------------------------------------------------|
| db.products.updateOne({ _id: UUID("...") }, { $inc: { "stock.Moscow": -1 } }) | targeted  | Хэш от _id направляет запрос в точный шард.                                           |
| db.products.findOne({ _id: UUID("...") })                                     | targeted  | Хэш от _id направляет запрос в один шард.                                             | 
| db.products.find({ category: "Electronics", price: { $lt: 1000 } })           | broadcast | Запрос идёт во все шарды, но каждый шард использует индекс { category: 1, price: 1 }. |

#### 2.6. Дополнительные индексы для ускорения доступа
```javascript
// Индекс для поиска по категории и цене (используется при broadcast-запросах)
db.products.createIndex({ category: 1, price: 1 })
```

### 3. Коллекция carts
#### 3.1. Схема документа в коллекции carts

```json
{
   "_id": "ObjectId",
   "user_id": "UUID | null",
   "session_id": "string | null",
   "items": [
      { "product_id": "UUID", "quantity": "int" }
   ],
   "status": "string (active|ordered|abandoned)",
   "created_at": "Date",
   "updated_at": "Date",
   "expires_at": "Date"
}
```
"_id" - уникальный идентификатор корзины

#### 3.2. Операции и их требования к шард-ключу

| Операция                                    | Какие поля фильтра  | Желаемый тип запроса | Почему      | Какие поля должны быть в шард-ключе |
|---------------------------------------------|---------------------|----------------------|-------------|-------------------------------------|
| Получение активной корзины (гость)          | session_id, status  | targeted             | очень часто | session_id                          |
| Получение активной корзины (авторизованный) | user_id, status     | targeted             | очень часто | user_id                             |
| Добавление/изменение/удаление товара        | _id                 | targeted             | очень часто | _id                                 |
| Слияние гостевой корзины с пользовательской | session_id, user_id | broadcast (допустим) | редко       | не требуется                        |

Ключевая проблема: нет единого поля, по которому можно шардировать, чтобы все частые операции стали targeted.

#### 3.3. Анализ кандидатов в шард-ключ

| Кандидат                  | Тип шардирования | Операции, которые станут targeted                | Проблемы                                                                                                            |
|---------------------------|------------------|--------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| { user_id: "hashed" }     | hashed           | получение корзины авторизованного                | гости (user_id = null) – все в один шард → перекос                                                                  |
| { session_id: "hashed" }  | hashed           | получение корзины гостя                          | авторизованные (session_id = null) – все в один шард → перекос                                                      |
| { _id: "hashed" }         | hashed           | добавление/изменение/удаление товара             | получение активной корзины – broadcast                                                                              |
| { status: 1, user_id: 1 } | ranged           | активные корзины авторизованных (префикс status) | активные корзины всех пользователей могут сконцентрироваться в одном шарде, гостевые корзины – аналогичная проблема |

#### 3.4. Выбранное решение

Шардирование

```javascript
sh.shardCollection("market.carts", { _id: "hashed" })
```

Почему именно этот ключ?

1. Операции модификации корзины (по _id) – самые частые
   * Добавление товара, изменение количества, удаление идут по _id. Хэширование равномерно распределяет эти операции по шардам и делает их targeted, что критично для производительности.

2. Получение активной корзины – broadcast, но это компромисс
   * Коллекция carts ограничена TTL (старые корзины удаляются), поэтому размер каждого шарда относительно невелик. Broadcast-запрос, хотя и идёт во все шарды, быстро выполняется благодаря индексам на (user_id, status) и (session_id, status).
   * Альтернативы (шардирование по user_id или session_id) создали бы сильный перекос (все гости или все авторизованные в одном шарде), что неприемлемо.

Варианты, которые оказались хуже:

* { user_id: "hashed" } – перекос из-за null для гостей.
* { session_id: "hashed" } – перекос из-за null для авторизованных.
* { status: 1, user_id: 1 } - диапазонное шардирование по статусу почти не даёт распределения (все активные корзины могут оказаться в одном шарде).

#### 3.5. Как выглядит выполнение запросов после шардирования

| Запрос                                                                  | Тип       | Объяснение                                                                           |
|-------------------------------------------------------------------------|-----------|--------------------------------------------------------------------------------------|
| db.carts.updateOne({ _id: ObjectId("...") }, { $push: { items: ... } }) | targeted  | Хэш от _id направляет запрос в точный шард                                           |
| db.carts.findOne({ user_id: "X", status: "active" })                    | broadcast | Запрос идёт во все шарды, каждый шард использует индекс { user_id: 1, status: 1 }    | 
| db.carts.findOne({ session_id: "Y", status: "active" })                 | broadcast | Запрос идёт во все шарды, каждый шард использует индекс { session_id: 1, status: 1 } |
| db.carts.deleteMany({ expires_at: { $lt: new Date() } })                | broadcast | Фоновая очистка TTL, допустима broadcast-операция                                    |

#### 3.6. Дополнительные индексы для ускорения доступа
```javascript
// Индексы для broadcast-запросов (поиск активной корзины)
db.carts.createIndex({ session_id: 1, status: 1 })
db.carts.createIndex({ user_id: 1, status: 1 })

// TTL-индекс для автоматического удаления старых корзин
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```
