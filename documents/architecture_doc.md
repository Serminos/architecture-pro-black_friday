# Задание 7. Проектирование схем коллекций для шардирования данных

## Введение

Дано:
БД MongoDB. 3 коллекции orders, products и carts с их описанием(опускаю для краткости).

Требуется:

* Спроектировать схемы коллекций products, orders и carts. Для этого проанализировать представленные атрибуты коллекций
  и выбрать потенциальных кандидатов для шард-ключей.
* Выберать стратегию шардирования для каждой коллекции, которая обеспечит эффективное распределение данных по шардам.
* Указать, почему выбранная стратегия и шард-ключ подходят под особенности коллекций и операций.

## Термины

Хэшированное шардирование (англ. key based sharding) — это разделение данных на шарды на основе хэш-функции от значения
шард-ключа. Обеспечивает равномерное распределение даже для монотонно возрастающих ключей.

Диапазонное шардирование (англ. range based sharding) — разделение данных на шарды на основе диапазонов значений
шард-ключа (chunks). Эффективно для запросов, фильтрующих по диапазону или сортирующих по ключу.

Targeted-запрос – запрос, который содержит полный шард-ключ (или его префикс) и направляется только в те шарды, где
могут быть данные. Быстрый, минимальная нагрузка на кластер.

Broadcast-запрос – запрос, который не содержит шард-ключ (или содержит его не полностью) и поэтому отправляется во все
шарды. Каждый шард выполняет поиск самостоятельно, результаты объединяются. Медленнее, создаёт дополнительную нагрузку.

## Особенности алгоритмиов шардированию данных

#### Хэшированное шардирование

* Равномерное распределение данных (устраняет hotspot).
* Затруднён поиск по диапазону (требует broadcast)..

Применение алгоритма оптимально для приложений, в которых крайне важно равномерно распределить данные. Например, при
хранении пользовательских сессий в веб-приложениях или товаров в магазине.

#### Диапазонное шардирование

* Быстрый поиск по диапазону и сортировка (при использовании префикса ключа).
* Риск дисбаланса (hotspot) при монотонном ключе..

Подходит для данных временных рядов или последовательных данных, таких как журналы, события с временными метками, цены
на товары и т. д.

#### Общий принцип

Стремиться к тому, чтобы наиболее частые и критичные операции были targeted-запросами, избегая broadcast для тяжелых
запросов. Также важно равномерно распределять данные и нагрузку по шардам, не допуская появления «горячих» шардов.

## Проект решения

### 1. Коллекция orders

#### 1.1. Схема документа в коллекции orders

```json
{
  "_id": "UUID",
  "customer_id": "UUID",
  "created_at": "Date",
  "items": [
    {
      "product_id": "UUID",
      "name": "string",
      "quantity": "int",
      "price": "Decimal128"
    }
  ],
  "status": "string (created|paid|shipped|delivered|cancelled)",
  "total": "Decimal128",
  "geo_zone": "string"
}
```

"_id" - id заказа

#### 1.2. Операции и их требования к шард-ключу

| Операция                                        | Какие поля фильтра                     | Желаемый тип запроса                | Почему                                                | Какие поля должны быть в шард-ключе    |
|-------------------------------------------------|----------------------------------------|-------------------------------------|-------------------------------------------------------|----------------------------------------|
| Создание заказа (вставка)                       | – (нет фильтра)                        | равномерное распределение по шардам | Избежать «горячей» точки (hotspot) при записи         | customer_id                            |
| Поиск истории заказов конкретного пользователя. | customer_id + сортировка по created_at | targeted                            | Частая операция, должна быть быстрой и масштабируемой | customer_id и created_at (как суффикс) |
| Отображение статуса заказа.                     | _id                                    | targeted (желательно)               | Обращение по уникальному идентификатору, тоже часто   | необязательно, допустим broadcast      |

#### 1.3. Анализ кандидатов в шард-ключ

| Кандидат                                 | Тип шардирования                   | Операции, которые станут targeted                                                   | Проблемы                                                                                          |
|------------------------------------------|------------------------------------|-------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------|
| { _id: "hashed" }                        | hashed                             | просмотр статуса                                                                    | История клиента – broadcast (и сортировка по дате неэффективна)                                   |
| { customer_id: 1, created_at: 1 }        | ranged (по клиенту, затем по дате) | история клиента (и сортировка по дате)                                              | Вставка: монотонность customer_id может дать 'горячий шард', если ID генерируются последовательно |
| { customer_id: "hashed", created_at: 1 } | hashed-префикс + диапазон          | история клиента (направляется в один шард по хэшу, внутри шарда сортировка по дате) | Просмотр статуса – broadcast                                                                      |

#### 1.4. Выбранное решение

Шардирование

```javascript
sh.shardCollection("market.orders", { customer_id: "hashed", created_at: 1 })
```

Почему именно этот составной ключ?

1. Хэширование customer_id
    * Равномерно распределяет заказы по шардам, полностью убирая hotspot (даже если ID клиента монотонны).
    * Любой запрос с фильтром по customer_id (даже без created_at) становится targeted, потому что хэш-префикс
      совпадает.

2. Диапазонная часть created_at
    * Позволяет внутри шарда эффективно выполнять сортировку по дате для истории заказов одного клиента.
    * Запрос { customer_id: X, created_at: { $gte: ... } } остаётся targeted.
3. Просмотр статуса по _id
    * Становится broadcast, но эта операция легковесна (один документ на шарде) и ускорена встроенным уникальным
      индексом.
    * Мы сознательно жертвуем этой операцией в пользу более частой истории заказов.

Варианты, которые оказались хуже:

* { _id: "hashed" } – история клиента стала бы broadcast, что неприемлемо для высоконагруженного сервиса.
* { customer_id: 1, created_at: 1 } (без хэша) – при монотонном customer_id новые заказы активных клиентов могли бы
  попадать в один шард (hotspot).

#### 1.5. Как выглядит выполнение запросов после шардирования

| Запрос                                                          | Тип                    | Объяснение                                                                                                                                |
|-----------------------------------------------------------------|------------------------|-------------------------------------------------------------------------------------------------------------------------------------------|
| db.orders.find({ customer_id: "123" }).sort({ created_at: -1 }) | targeted               | Хэш от customer_id направляет запрос в точный шард, внутри шарда используется индекс по created_at.                                       |
| db.orders.findOne({ _id: "abc" })                               | broadcast              | Запрос идёт во все шарды, но уникальный индекс на _id позволит быстро найти документ на каждом шарде (только один шард вернёт результат). | 
| db.orders.insert({ ... })                                       | распределённая вставка | Хэш от customer_id определяет шард, в который попадёт новый заказ (без «горячей» точки).                                                  |

#### 1.6. Дополнительные индексы для ускорения доступа

Исходя из указанных в задании типовых операций не требуются

## 2. Коллекция products

#### 2.1. Схема документа в коллекции products

```json
{
  "_id": "UUID",
  "name": "string",
  "category": "string",
  "price": "Decimal128",
  "stock": [
    {
      "geo_zone": "string",
      "quantity": "int"
    }
  ],
  "attributes": {
    "color": "string",
    "size": "string"
  },
  "created_at": "Date",
  "updated_at": "Date"
}
```

"_id" - уникальный идентификатор товара

#### 2.2. Операции и их требования к шард-ключу

| Операция                                   | Какие поля фильтра | Желаемый тип запроса | Почему                           | Какие поля должны быть в шард-ключе |
|--------------------------------------------|--------------------|----------------------|----------------------------------|-------------------------------------|
| Обновление остатка товара при покупке      | _id                | targeted             | очень часто, критично к задержке | _id                                 |
| Чтение карточки товара (страница продукта) | _id                | targeted             | часто, пользовательский опыт     | _id                                 |
| Поиск товаров по категории и диапазону цен | category, price    | broadcast (допустим) | менее частый, можно кешировать   | не требуется                        |

#### 2.3. Анализ кандидатов в шард-ключ

| Кандидат                | Тип шардирования | Операции, которые станут targeted   | Проблемы                                                                  |
|-------------------------|------------------|-------------------------------------|---------------------------------------------------------------------------|
| { _id: "hashed" }       | hashed           | обновление остатка, карточка товара | поиск по категории/цене – broadcast                                       |
| { category: "hashed" }  | hashed           | поиск по категории                  | обновление остатка и карточка – broadcast (плохо)                         |
| { category: 1, _id: 1 } | ranged           | поиск по категории (префикс)        | обновление остатка – broadcast, плюс jumbo-куски на популярных категориях |

#### 2.4. Выбранное решение

Шардирование

```javascript
sh.shardCollection("market.products", { _id: "hashed" })
```

Почему именно этот ключ?

1. Операции с _id – самые частые и критичные
    * Обновление остатков и чтение карточки товара выполняются постоянно. Хэшированный _id делает эти запросы targeted и
      идеально распределяет нагрузку по шардам (даже если _id генерируется монотонно, хэш устраняет hotspot).

2. Поиск по категории и цене – broadcast, но это компромисс
    * Такой поиск выполняется реже, его результаты можно кешировать. На каждом шарде он будет использовать вторичный
      индекс { category: 1, price: 1 }, что приемлемо.

Варианты, которые оказались хуже:

* { category: "hashed" } – превратила бы частые обновления остатков в broadcast, что неприемлемо.
* { category: 1, _id: 1 } (диапазонное) – привела бы к jumbo-кускам на больших категориях (например, «Электроника») и
  перекосу записи.

#### 2.5. Как выглядит выполнение запросов после шардирования

| Запрос                                                                        | Тип       | Объяснение                                                                            |
|-------------------------------------------------------------------------------|-----------|---------------------------------------------------------------------------------------|
| db.products.updateOne({ _id: UUID("...") }, { $inc: { "stock.Moscow": -1 } }) | targeted  | Хэш от _id направляет запрос в точный шард.                                           |
| db.products.findOne({ _id: UUID("...") })                                     | targeted  | Хэш от _id направляет запрос в один шард.                                             | 
| db.products.find({ category: "Electronics", price: { $lt: 1000 } })           | broadcast | Запрос идёт во все шарды, но каждый шард использует индекс { category: 1, price: 1 }. |

#### 2.6. Дополнительные индексы для ускорения доступа

```javascript
// Индекс для поиска по категории и цене (используется при broadcast-запросах)
db.products.createIndex({ category: 1, price: 1 })
```

## 3. Коллекция carts

#### 3.1. Схема документа в коллекции carts

```json
{
  "_id": "ObjectId",
  "user_id": "UUID | null",
  "session_id": "string | null",
  "items": [
    {
      "product_id": "UUID",
      "quantity": "int"
    }
  ],
  "status": "string (active|ordered|abandoned)",
  "created_at": "Date",
  "updated_at": "Date",
  "expires_at": "Date"
}
```

"_id" - уникальный идентификатор корзины

#### 3.2. Операции и их требования к шард-ключу

| Операция                                    | Какие поля фильтра  | Желаемый тип запроса | Почему      | Какие поля должны быть в шард-ключе |
|---------------------------------------------|---------------------|----------------------|-------------|-------------------------------------|
| Получение активной корзины (гость)          | session_id, status  | targeted             | очень часто | session_id                          |
| Получение активной корзины (авторизованный) | user_id, status     | targeted             | очень часто | user_id                             |
| Добавление/изменение/удаление товара        | _id                 | targeted             | очень часто | _id                                 |
| Слияние гостевой корзины с пользовательской | session_id, user_id | broadcast (допустим) | редко       | не требуется                        |

Ключевая проблема: нет единого поля, по которому можно шардировать, чтобы все частые операции стали targeted.

#### 3.3. Анализ кандидатов в шард-ключ

| Кандидат                  | Тип шардирования | Операции, которые станут targeted                | Проблемы                                                                                                            |
|---------------------------|------------------|--------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| { user_id: "hashed" }     | hashed           | получение корзины авторизованного                | гости (user_id = null) – все в один шард → перекос                                                                  |
| { session_id: "hashed" }  | hashed           | получение корзины гостя                          | авторизованные (session_id = null) – все в один шард → перекос                                                      |
| { _id: "hashed" }         | hashed           | добавление/изменение/удаление товара             | получение активной корзины – broadcast                                                                              |
| { status: 1, user_id: 1 } | ranged           | активные корзины авторизованных (префикс status) | активные корзины всех пользователей могут сконцентрироваться в одном шарде, гостевые корзины – аналогичная проблема |

#### 3.4. Выбранное решение

Шардирование

```javascript
sh.shardCollection("market.carts", { _id: "hashed" })
```

Почему именно этот ключ?

1. Операции модификации корзины (по _id) – самые частые
    * Добавление товара, изменение количества, удаление идут по _id. Хэширование равномерно распределяет эти операции по
      шардам и делает их targeted, что критично для производительности.

2. Получение активной корзины – broadcast, но это компромисс
    * Коллекция carts ограничена TTL (старые корзины удаляются), поэтому размер каждого шарда относительно невелик.
      Broadcast-запрос, хотя и идёт во все шарды, быстро выполняется благодаря индексам на (user_id, status) и (
      session_id, status).
    * Альтернативы (шардирование по user_id или session_id) создали бы сильный перекос (все гости или все авторизованные
      в одном шарде), что неприемлемо.

Варианты, которые оказались хуже:

* { user_id: "hashed" } – перекос из-за null для гостей.
* { session_id: "hashed" } – перекос из-за null для авторизованных.
* { status: 1, user_id: 1 } - диапазонное шардирование по статусу почти не даёт распределения (все активные корзины
  могут оказаться в одном шарде).

#### 3.5. Как выглядит выполнение запросов после шардирования

| Запрос                                                                  | Тип       | Объяснение                                                                           |
|-------------------------------------------------------------------------|-----------|--------------------------------------------------------------------------------------|
| db.carts.updateOne({ _id: ObjectId("...") }, { $push: { items: ... } }) | targeted  | Хэш от _id направляет запрос в точный шард                                           |
| db.carts.findOne({ user_id: "X", status: "active" })                    | broadcast | Запрос идёт во все шарды, каждый шард использует индекс { user_id: 1, status: 1 }    | 
| db.carts.findOne({ session_id: "Y", status: "active" })                 | broadcast | Запрос идёт во все шарды, каждый шард использует индекс { session_id: 1, status: 1 } |
| db.carts.deleteMany({ expires_at: { $lt: new Date() } })                | broadcast | Фоновая очистка TTL, допустима broadcast-операция                                    |

#### 3.6. Дополнительные индексы для ускорения доступа

```javascript
// Индексы для broadcast-запросов (поиск активной корзины)
db.carts.createIndex({ session_id: 1, status: 1 })
db.carts.createIndex({ user_id: 1, status: 1 })

// TTL-индекс для автоматического удаления старых корзин
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```

# Задание 8. Выявление и устранение «горячих» шардов

## Введение

Дано:
БД MongoDB. Из-за категории «Электроника» произошла перегрузка одного из шардов MongoDB, так как 70% запросов
приходилось именно на эти товары.

Требуется:

* Разработайте набор метрик, чтобы отслеживать состояние шардов.
* Предложите механизмы автоматического перераспределения данных.

## Проект решения

### 1. Метрики мониторинга для обнаружения дисбаланса

| Уровень                   | Метрика                                  | Команда / источник                                | Порог тревоги                                                       |
|---------------------------|------------------------------------------|---------------------------------------------------|---------------------------------------------------------------------|
| Приложение (данные)       | Размер данных, чанков на шард            | sh.status(), db.collection.getShardDistribution() | data skew > 1.5 (один шард занимает в 1.5 раза больше среднего)     |
| Приложение (нагрузка)     | Количество операций (opcounters) на шард | mongostat --discover, Prometheus                  | load skew > 1.5 (один шард обрабатывает в 1.5 раза больше запросов) |
| Приложение (структура)    | Наличие jumbo-кусков                     | sh.status(true)                                   | Любой "jumbo": true                                                 |
| Приложение (запросы)      | Доля broadcast-запросов                  | explain() на mongos                               | > 20% запросов не содержат шард-ключ                                |
| Приложение (балансировка) | Активность балансировщика                | sh.isBalancerRunning()                            | Отключён более суток                                                |
| Железо (CPU)              | Загрузка CPU на узле                     | top, node_exporter, mongodb_exporter (метрики ОС) | > 80% на одном шарде, на других < 50%                               |
| Железо (диск)             | iowait, латентность чтения/записи        | iostat -x 1, mongostat (столбцы arw/aw)           | iowait > 10%; latency > 50 мс                                       |
| Железо (сеть)             | Входящий/исходящий трафик                | nload, iftop, метрики сетевого интерфейса         | Один шард получает > 70% всего трафика кластера                     |
| Железо (память)           | Использование RAM, своп                  | free -m, db.serverStatus().mem, RSS               | свободная память < 20%, есть своп                                   |
| Железо (диск)             | Свободное место                          | df -h, db.stats()                                 | заполнение > 80%                                                    |
Алерты:
* max(opcounters) / avg(opcounters) > 1.5 в течение 5 минут → load skew.
* max(data_size) / min(data_size) > 1.5 → data skew.
* cpu_usage > 80% на одном шарде при среднем < 50% на других → возможен нагрузочный перекос или проблемы с железом.
* iowait > 10% или disk_latency > 50 мс → проблемы с диском.
* свободное место < 20% → риск остановки записи.

### 2. Механизмы автоматического перераспределения данных

| Механизм                         | Автоматический?                  | Что делает                                            | Когда применять                                                       |
|----------------------------------|----------------------------------|-------------------------------------------------------|-----------------------------------------------------------------------|
| Балансировщик (balancer)         | да (штатный)                     | Выравнивает количество чанков по шардам               | Перекос в данных                                                      |
| Зоны (zone sharding)             | да (через balancer)              | Закрепляет диапазоны ключа за группой шардов          | Перекос в нагрузщке по категории (разнести «Электронику» на 2+ шарда) |
| Уменьшение chunksize             | да (новые чанки дробятся раньше) | Предотвращает появление jumbo-кусков                  | При частых jumbo-кусках                                               |
| Чтение с реплик (readPreference) | да (на уровне драйвера)          | Разгружает primary, перенаправляя чтения на secondary | hot document, нагрузочный перекос                                     |
| reshardCollection                | да (онлайн-миграция)             | Полностью меняет шард-ключ и перераспределяет данные  | Системный провал шард-ключа (например, перейти на product_id: hashed) |
| Пользовательский авто-скрипт     | частично (требуется настройка)   | Перемещает «тяжёлые» чанки, меняет зоны               | Сложная бизнес-логика, не покрываемая стандартными средствами         |

Примеры команд для автоматизации

```javascript
// 1. Включить балансировщик и настроить окно работы (например, ночью)
sh.startBalancer()
sh.setBalancerWindow("01:00", "06:00")

// 2. Разнести категорию «Электроника» на два шарда через зоны
sh.addShardToZone("shard1", "hot")
sh.addShardToZone("shard2", "hot")
sh.updateZoneKeyRange("market.products",
{ category: "Электроника" }, { category: "Электроника\uFFFF" }, "hot")

// 3. Уменьшить размер чанка (чтобы чанки дробились чаще)
use config
db.settings.updateOne({ _id: "chunksize" }, { $set: { value: 32 } }, { upsert: true })

// 4. Сменить шард-ключ онлайн (например, на hashed product_id) – крайняя мера
db.adminCommand({
reshardCollection: "market.products",
key: { product_id: "hashed" }
})

// 5. Авто-скрипт (псевдокод) – при load skew перемещает самый активный чанк
if (load_skew_detected()) {
hot_chunk = find_hottest_chunk()
target_shard = get_least_loaded_shard()
sh.moveChunk("market.products", hot_chunk.min, target_shard)
}
```

### 3. Алгоритм реагирования

1. Алерт – метрики показывают перекос.
2. Определяем тип перекоса:
* Размер данных различается → data skew → включить балансировщик, при необходимости уменьшить chunksize.
* Нагрузка различается при ровных данных → load skew → использовать зоны или reshardCollection.
3. Проверить аппаратные метрики (CPU, iowait, память) – возможно, проблема не в данных, а в конкретном узле (например, медленный диск)
4. Если load skew:
* Найти горячую категорию / диапазон с помощью профайлера или mongotop.
* Применить зоны (разнести категорию на несколько шардов).
* Если один товар создаёт пик → кеш Redis + чтение с реплик.
5. Если данные перекошены системно (jumbo-куски):
* Уменьшить chunksize, разбить крупные чанки вручную или дождаться автосплита.
* При необходимости добавить суффикс к шард-ключу (refineCollectionShardKey).
6. Если ни один из способов не помогает → перейти на hashed-шардирование через reshardCollection.
7. После устранения – зафиксировать причину, обновить пороги алертов.

# Задание 9. Настройка чтения с реплик и консистентность

## Введение

Дано:
БД MongoDB. Коллекции products и orders и carts.

Требуется:
1. Для коллекций products и orders и carts определите:
* Какие операции чтения могут использовать secondary реплику для чтения.
* Какие операции чтения должны читать только с primary.
* Укажите, какая задержка репликации допустима для операций на secondary.
2. Обоснуйте выбор, опираясь на:
* Требования к консистентности данных.
* Частоту обновлений.
* Бизнес-логику (например, риск продажи недоступного товара или отображение устаревшего статуса заказа пользователю).

## Проект решения
### 1. Общие принципы

- Primary – источник истины, все записи идут только на него.
- Secondary – асинхронно реплицируют данные от primary, возможна задержка (обычно миллисекунды, но при высокой нагрузке может достигать секунд).
- Допустимая задержка – время, на которое данные на secondary могут отставать от primary. Зависит от того, насколько критично пользователю видеть самые свежие изменения.

### 2. Таблица операций чтения

| Коллекция | Операция чтения                                                             | Чтение с primary | Чтение с secondary | Допустимая задержка | Обоснование                                                                                                                                                     |
|-----------|-----------------------------------------------------------------------------|:----------------:|:------------------:|---------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| orders    | Просмотр истории заказов пользователем                                      |                  |         +          | до 10 секунд        | Статус заказа может измениться не мгновенно; клиент понимает, что информация обновляется с небольшой задержкой (например, после оплаты).                        |
|           | Просмотр статуса заказа (по order_id)                                       |                  |         +          | до 10 секунд        | Аналогично истории – допустимо отставание, особенно если заказ уже в обработке.                                                                                 |
|           | Проверка статуса для внутренних процессов (например, отгрузка, бухгалтерия) |        +         |                    | 0 секунд            | Оператор или автоматика должны работать с точными данными, чтобы не допустить двойной отправки или ошибок в учёте.                                              |
| products  | Просмотр каталога (фильтр по категории/цене)                                |                  |         +          | до 5 секунд         | Клиенту не критично видеть изменение остатка или цены с точностью до миллисекунды. Небольшая задержка не влияет на покупку (при оформлении отдельная проверка). |
|           | Карточка товара (детальная информация)                                      |                  |         +          | до 5 секунд         | Аналогично каталогу – цена и описание меняются редко, небольшое отставание допустимо.                                                                           |
|           | Проверка остатка при добавлении в корзину                                   |        +         |                    | 0 секунд            | Пользователь должен видеть реальный остаток, иначе при оформлении заказа может возникнуть конфликт. Чтение с primary гарантирует точность.                      |
|           | Резервирование товара при создании заказа                                   |        +         |                    | 0 секунд            | Критически важно: проверка и списание остатка должны происходить на актуальных данных, чтобы избежать overselling.                                              |
| carts     | Получение текущей корзины пользователя (при показе страницы корзины)        |        +         |                    | 0 секунд            | Пользователь ожидает видеть актуальный состав и количество. Даже задержка в 1 секунду может привести к путанице (добавил товар – не видит).                     |
|           | Проверка корзины перед оформлением заказа                                   |        +         |                    | 0 секунд            | Требуется точный список товаров и их количество для расчёта суммы и резервирования.                                                                             |
|           | Слияние гостевой корзины с пользовательской                                 |        +         |                    | 0 секунд            | Операция чтения и последующей записи; должна использовать primary для консистентности и предотвращения потери данных.                                           |


### 3. Допустимая задержка репликации

- Для чтений с secondary (каталог, карточка, история заказов) – до 5–10 секунд.
- Для критических операций (проверка остатка, резервирование, корзина) – 0 секунд, только primary.

### 4. Обоснование выбора

1. Коллекция products
   - Чтения каталога – не транзакционные, пользователь редко замечает задержку в несколько секунд. Списание остатков и резервирование должны быть строго консистентны → primary.
   - Бизнес-риск при чтении с secondary для каталога минимален (может показать устаревший остаток, но при попытке купить будет реальная проверка).

2. Коллекция orders
   - История заказов и статус – не критичны к абсолютной актуальности (клиент может обновить страницу).
   - Внутренние финансовые и логистические процессы требуют сильной консистенции → primary.

3. Коллекция carts
   - Корзина – это временные данные, но они интерактивны. Пользователь постоянно их меняет. Даже небольшая задержка разрушает ожидание «сразу вижу результат» → только primary.
   - В случае слияния корзин также нужна атомарность и актуальность, иначе возможна потеря добавленных товаров.

### 5. Дополнительные рекомендации

- В драйвере MongoDB можно указать readPreference: secondaryPreferred для каталога и истории заказов, чтобы разгружать primary.
- Для корзины и критических операций – readPreference: primary.
- Настроить мониторинг lag репликации (rs.printReplicationInfo()), при превышении 10 секунд – алерт.

Данный подход балансирует производительность (разгрузка primary) и консистентность, минимизируя риски для бизнеса.


# Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

## Введение
Во время «чёрной пятницы» интернет-магазин использовал MongoDB с шардированием на основе диапазонов (Range-Based Sharding). При резком увеличении нагрузки (50 000 запросов/сек.) возникла высокая задержка при масштабировании:

При добавлении новых шардов MongoDB полностью перераспределяла данные между всеми узлами, что вызывало просадку latency в пик нагрузки, так как система тратила ресурсы на перемещение данных.

Руководство решило перейти на БД Cassandra, чтобы обеспечить:
* Высокую отказоустойчивость (leaderless‑репликация).
* Быстрое горизонтальное масштабирование без полного перераспределения данных.
* Равномерное распределение данных.

Ниже определено, какие сущности интернет-магазина стоит перенести в Cassandra, спроектирована модель данных и выбраны стратегии обеспечения целостности.

## 10.1. Выбор сущностей для Cassandra
### Исходные условия
- Используются две БД: MongoDB (текущая) и Cassandra (целевая для части данных).
- MongoDB остаётся для сущностей, требующих сильной консистенции, сложных запросов (фильтрация, агрегации) и атомарных обновлений.
- Cassandra выбирается для сущностей с высокой нагрузкой на запись, линейной масштабируемостью, допустимой итоговой согласованностью и простым доступом по ключу.

### Критерии распределения

|   | Критерий                     | MongoDB                                              | Cassandra                                        |
|:-:|------------------------------|------------------------------------------------------|--------------------------------------------------|
| 1 | Согласованность              | Сильная (read-after-write, транзакции)               | Итоговая (eventual consistency)                  |
| 2 | Частота записи               | Умеренная или низкая                                 | Очень высокая (десятки тысяч операций/с)         |
| 3 | Изменяемость записей         | Частые обновления/удаления одних и тех же документов | Преимущественно вставки, редко обновления        |
| 4 | Сложность запросов           | Фильтрация, сортировка, агрегации, вторичные индексы | Только по partition key (или с кластеризацией)   |
| 5 | Требования к масштабированию | Вертикальное + шардирование с перебалансировкой      | Горизонтальное без глобального перераспределения |
| 6 | Геораспределённость          | Возможна, но сложнее                                 | Встроенная поддержка                             |

### Распределение сущностей

| Сущность                      | Переносим? | Обоснование                                                                           |
|-------------------------------|:----------:|---------------------------------------------------------------------------------------|
| Активные заказы и оплата      |     -      | Критерии 1, 4 (нужна строгая консистенция, сложные запросы по статусам)               |
| История заказов (завершённые) |     +      | Критерии 2, 3, 6 (высокая частота вставок, неизменяемость, простота доступа по ключу) |
| Товары (каталог)              |     -      | Критерий 4 (сложные фильтры, агрегации)                                               |
| Остатки товаров               |     -      | Критерии 1, 2 (атомарность, строгая консистенция) – LWT в Cassandra слишком медленные |
| Корзины                       |     -      | Критерии 1, 3 (read-after-write, частые обновления)                                   |
| Пользовательские сессии       |     +      | Критерии 2, 3, 6 (высокая частота записи, TTL, простота доступа)                      |

В некоторых высоконагруженных проектах корзины хранят в Cassandra, так как они читаются по ключу user_id и допускают итоговую согласованность. Однако в данном решении мы оставляем корзины в MongoDB, чтобы гарантировать строгую консистенцию (read-after-write) и упростить логику резервирования товаров

### Итоговое решение

В Cassandra переносим:
- Историю заказов (только завершённые, неизменяемые записи).
- Сессии пользователей (высокая нагрузка, TTL, ключевой доступ).

Оставляем в MongoDB:
- Активные заказы и оплату.
- Каталог товаров и остатки.
- Корзины.

## 10.2. Модель данных в Cassandra
## Задача
Разработайте концептуальную модель для выбранных критически важных сущностей.
Определите partition key и кластерные ключи для каждой сущности, объяснив, как они будут обеспечивать равномерное распределение данных и эффективный доступ в условиях экстремальной нагрузки.
Обоснуйте выбор модели с точки зрения возможных «горячих» партиций и минимизации влияния решардинга при изменении топологии кластера.

На основе решения из 10.1 в Cassandra переносятся история заказов и сессии пользователей. 
С учётом паттернов доступа, равномерного распределения и минимизации горячих партиций разработаны модели данных.

### 1.История заказов (order_history)
#### Типовые запросы:
- Вставка записи о завершённом заказе (очень высокая интенсивность).
- Получение последних N заказов конкретного пользователя, отсортированных от новых к старым.

#### Модель таблицы (CQL):
```cql
CREATE TABLE order_history (
    user_id     uuid,
    bucket      int,               -- год, ограничивает размер партиции
    order_id    timeuuid,          -- кластерный ключ, содержит временную метку
    created_at  timestamp,         -- дублирует время из order_id для удобства
    total       decimal,
    status      text,
    items       text,              -- позиции заказа в JSON
    PRIMARY KEY ((user_id, bucket), order_id)
) WITH CLUSTERING ORDER BY (order_id DESC);
```
#### Обоснование
* Почему нет горячих партиций:
  - Partition key состоит из двух полей: user_id и bucket (год).
  - bucket ограничивает размер партиции – даже если у клиента тысячи заказов, в одной партиции оказываются записи только за один год.
  - Комбинация (user_id, bucket) даёт огромное количество уникальных значений (количество клиентов × количество лет), поэтому хэши распределяются равномерно по всем узлам, и ни одна партиция не получает непропорционально большую нагрузку.
  - Если в будущем понадобится ещё мельче дробление (например, по месяцам), можно изменить bucket на year_month без изменения логики приложения – это легко сделать на этапе миграции.
* Минимизация влияния решардинга:
  - При добавлении нового узла в кластер Cassandra перемещает только некоторые диапазоны токенов, а не все партиции. Поскольку каждая партиция здесь маленькая (ограничена годом) и их много, перераспределение происходит небольшими порциями, не вызывая глобальной просадки производительности.
  - В MongoDB при добавлении шарда нужно было массово перераспределять все чанки, что и приводило к падению latency. В Cassandra этого нет.

Дублирование created_at:  
Хранение отдельного поля created_at упрощает фильтрацию и чтение данных без дополнительного парсинга UUID.

### 2. Сессии пользователей (sessions)

#### Типовые запросы:
- Создание сессии (вставка по session_id).
- Чтение сессии по session_id для проверки аутентификации.
- Продление жизни сессии (сброс TTL) – не при каждом запросе, а периодически (например, раз в 5 минут) или при обновлении содержимого сессии.
- Автоматическое удаление устаревших сессий.

#### Модель таблицы (CQL):
```cql
CREATE TABLE user_sessions (
    session_id  uuid PRIMARY KEY,
    user_id     uuid,
    created_at  timestamp,
    user_agent  text,
    data        text               -- содержимое сессии в JSON
) WITH default_time_to_live = 86400;   -- автоудаление через 24 часа
```
#### Обоснование
* Почему нет горячих партиций:
  - Partition key – session_id, случайный UUID. Каждая партиция содержит ровно одну запись.
  - Случайность UUID обеспечивает идеально равномерное распределение токенов по кольцу. Никакой «горячей» партиции возникнуть не может, так как нагрузка на один конкретный ключ – это ровно одна сессия.

* Минимизация влияния решардинга:
  - Так как каждая сессия – отдельная партиция, добавление узла в кластер затронет лишь малую долю случайно выбранных сессий. Перемещение происходит независимо для каждой партиции, без массового перераспределения.
  - В отличие от MongoDB, где при добавлении шарда перебалансировка затрагивала все данные, здесь решардинг практически незаметен для пользователей.

### Почему выбранная модель устойчива к горячим партициям и решардингу
| Сущность        | Почему нет горячих партиций                                                                                                                       | Почему решардинг минимально влияет                                                                                                                   |
|-----------------|---------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| История заказов | Partition key (user_id, bucket) разбивает данные на множество маленьких партиций (по году). Даже у одного клиента партиции ограничены по размеру. | При добавлении узла перемещаются только отдельные диапазоны токенов, а не все данные. Миграция идёт маленькими партициями – нет глобальной просадки. |
| Сессии          | Partition key session_id – случайный UUID дает максимальное равномерное распределение, каждая партиция – одна запись.                             | Добавление узла затрагивает малую долю случайных ключей, перераспределение незаметно.                                                                |

Таким образом, предложенная модель соответствует требованиям высокой нагрузки (50000 запросов/с) и обеспечивает линейную масштабируемость без простоев, устраняя проблему, из-за которой сайт падал на MongoDB.

## 10.3. Стратегии обеспечения целостности данных в Cassandra
## Задача
Какие стратегии (Hinted Handoff, Read Repair, Anti-Entropy Repair) можно применить для обеспечения целостности данных?
Для каких сущностей вы выберете одну стратегию, а для каких — другую?
Обоснуйте свой выбор с учётом компромиссов между latency запросов и уровнем гарантии согласованности.

### Кратко о механизмах
| Стратегия           | Принцип                                                                       | Влияние на latency              | Уровень гарантии            |
|---------------------|-------------------------------------------------------------------------------|---------------------------------|-----------------------------|
| Hinted Handoff      | При недоступности реплики координатор сохраняет запись и позже пересылает её. | Низкое (асинхронно)             | Защита от временных отказов |
| Read Repair         | При чтении сравниваются данные со всех реплик, расхождения исправляются.      | Среднее (дополнительные чтения) | Высокая (на момент чтения)  |
| Anti‑Entropy Repair | Фоновое сравнение хэшей Merkle tree (по расписанию).                          | Не влияет на запросы            | Полное согласование         |

### Выбор стратегий для наших сущностей
| Сущность        | Hinted Handoff | Read Repair | Anti‑Entropy Repair | Уровень согласованности | Обоснование                                                                                                                                                                                                                                                               |
|-----------------|----------------|-------------|---------------------|-------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| История заказов | да             | нет (NONE)  | раз в неделю        | LOCAL_QUORUM            | Заказы важны, нельзя потерять. Read Repair отключён, чтобы не увеличивать latency чтения. Согласованность поддерживается плановым repair. LOCAL_QUORUM даёт гарантию, что большинство реплик подтвердили запись.                                                          |
| Сессии          | да             | нет (NONE)  | нет                 | ONE                     | Скорость критична. Read Repair отключён, чтобы не увеличивать latency чтения. Согласованность поддерживается плановым repair. Сессии живут 24 часа (TTL), расхождения исчезают сами. Hinted Handoff оставляем (дешёвый). Anti‑Entropy не нужен – данные удаляются по TTL. |

### Пояснение компромисса

- Для истории заказов – надёжность важнее скорости. LOCAL_QUORUM защищает от чтения устаревшего списка заказов. Read Repair отключён, чтобы не увеличивать latency чтения; согласованность поддерживается плановым repair (раз в неделю).
- Для сессий – скорость первична. ONE обеспечивает минимальную задержку, а потеря сессии не страшна (пользователь просто залогинится заново). TTL автоматически удаляет старые данные.

### Пример настройки (CQL)

```cql
-- История заказов
ALTER TABLE order_history 
WITH read_repair = 'NONE' 
AND gc_grace_seconds = 864000;

-- Для сессий (аналогично)
ALTER TABLE user_sessions 
WITH read_repair = 'NONE';
```

Hinted Handoff не отключается (работает по умолчанию). Anti‑Entropy repair запускается внешним планировщиком (nodetool repair).
